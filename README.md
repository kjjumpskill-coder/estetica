# Estetika

Лендінг салону краси **Estetika** — Кірілова Ольга, Дніпро.
Косметологія, перманентний макіяж, ін'єкційні методики.

PHP 8.2 без фреймворку, MySQL 8, vanilla JS, власний CSS.
Одна зовнішня залежність — `vlucas/phpdotenv`.

---

## Чому без фреймворку

Сайт живе на shared-хостингу з лімітом **100 CPU-хвилин на добу**. Bootstrap
повноцінного фреймворку на кожному запиті вигорає цей ліміт за кілька годин
рекламного трафіку. Тому тут власний мінімальний роутер, а головна сторінка
кешується у статичний HTML, який веб-сервер віддає, не запускаючи PHP узагалі.

З тієї ж причини немає Google Analytics: аналітика власна, без сторонніх куків,
а отже й без банера згоди. Відвідувач розрізняється за необоротним хешем, який
змінюється щодоби — цього досить для потрібних метрик і замало для стеження.

## Запуск

Потрібен лише Docker.

```bash
cp .env.example .env
docker compose up -d
docker compose exec app composer install
docker compose exec app php bin/migrate.php
open http://localhost:8080
```

## Структура

```
public_html/     document root: front controller, асети, згенеровані WebP
app/Core/        роутер, БД, шаблонізатор, CSRF, кеш, обробка зображень
app/Controllers/ по контролеру на розділ
app/Repositories/по репозиторію на сутність
app/Views/       layouts + sections + partials; кожна секція — окремий файл
bin/             CLI: міграції, імпорт фото, скріншоти, перевірки
migrations/      пронумеровані .sql, застосовуються один раз
storage/         оригінали фото й логи, поза вебом
```

## Команди

```bash
docker compose exec app php bin/migrate.php            застосувати міграції
docker compose exec app php bin/migrate.php --status   що застосовано
./bin/heic-convert.sh                                  HEIC → JPG (macOS)
docker compose exec app php bin/import-photos.php      імпорт фото
node bin/smoke.mjs                                     перевірка інтерактиву
node bin/shots.mjs                                     скріншоти трьох розмірів
./deploy.sh --dry-run                                  що поїде на сервер
```

## Робота з фото

Оригінали складаються в `storage/originals/` за категоріями. Підпапка всередині
`works/` визначає послугу: `works/brows/`, `works/botox/` і так далі.

`bin/import-photos.php` сканує теку, генерує WebP у чотирьох розмірах,
**повністю знімає EXIF** — насамперед GPS-координати, бо фото з телефону містять
місце зйомки, — і записує рядок у базу з `is_published = 0`. Що саме публікувати,
вирішує власниця в адмінці. Дедуплікація йде по SHA-1 вмісту, тому повторний
запуск нічого не дублює.

HEIC обробляється окремо: GD на shared-хостингу цей формат не відкриває, тому
конвертація робиться локально на macOS через `sips`.

## Три поля, яких немає у типовій схемі

- **`works.layout`** — реальний матеріал це готові інстаграмні колажі, де «до»
  і «після» вже склеєні в одну картинку. Слайдер-порівняння на них неможливий.
  Поле розрізняє `collage`, `single` і `pair`, тож коли з'являться роздільні
  знімки, слайдер вмикається без переробки галереї.
- **`reviews.body`** — відгуки зберігаються текстом, а не скріншотами листувань.
  І приватніше, і дає індексований `schema.org/Review`.
- **`media.orientation`** — частина знімків зроблена догори ногами, і це не
  EXIF-орієнтація: камера справді так знімала. Потрібен ручний кут.

## Тестове середовище

Будь-яке `APP_ENV`, відмінне від `production`, закриває майданчик: заборона
індексації, вимкнений статичний кеш і HTTP Basic, якщо заданий `STAGING_PASS`.

Кеш вимикається саме з міркувань безпеки — готовий `cache/index.html` веб-сервер
віддає ще до старту PHP, тобто в обхід пароля. З тієї ж причини маркер `.staging`
переводить `/media` та `/assets` через front controller: інакше фото відкривалися б
за прямим посиланням.

Як підняти — [docs/deploy-staging.md](docs/deploy-staging.md).
